What the agent does¶

The agent touches nothing outside these tools, which the editor gives it: it has no access to your files, nor to the computer's commands. Every change it makes goes through the editor's history and is undone with Ctrl+Z, or with the Undo these changes button under its answer. In the conversation, each tool shows as a short sentence: that is the "In the conversation" column.

What the agent reads about each tool¶

The exact description the agent receives for each tool.

scene_get¶

Read the scene: revision, player, world settings, scripts, a summary of the objects grouped by name (with counts, tags and asset), and one page of objects with their world bounds. Call this before editing. Use name_contains, tag, limit and offset to read other objects. To change many objects at once, you do not need their ids: entities_update and entities_delete accept a where filter.

project_rules¶

Read how to work in this editor: the method for large requests, how to prove your work, how to build worlds. Read this first if you have not been given it.

plan_set¶

Write or rewrite your plan for a large request: the user sees it in the chat, and it survives if the conversation restarts. 4 to 10 steps, in order, each with a check saying how you will prove it works. Dropping a step that is not done requires dropped_because. Steps already done keep their evidence.

plan_step¶

Update one step of your plan, by its number from 1. Mark a step doing when you start it. done requires evidence: what you actually observed that proves it works, not what you intended, and is refused while objects float. blocked requires evidence too: what stopped you.

assets_folders¶

List the folders of the asset library: their paths, how many models each one has, and how many are in formats the engine cannot read yet. Call this when the user names a pack or a folder. If what they name is not there, tell them instead of using something else.

assets_search¶

Search every folder of the asset library by words in the file path (all words must match, including words of the folder or pack name). Returns objects you can place; with kind "image", images for game.hud_image and interface screens (UI packs, icons), each with its size in pixels; with kind "sound", sounds for game.sound and game.music (WAV, MP3, OGG, FLAC); with kind "video", videos for game.video and game.hud_video (MP4, M4V, MOV).

asset_info¶

Inspect an asset before placing it: real size in metres, pivot, triangles, skeleton. Check sizes: assets from different packs may not share a scale. For an animated character, bone_positions gives where each bone starts at rest, in the model's own frame, in metres (unscaled): use it to find the hand when the model has no hand bone. legs_for_feet_on_ground counts the legs the engine recognises for placeFeet.

entities_create¶

Add objects to the scene, as a single undoable step. Prefer one call with many objects over many calls.

entities_scatter¶

Fill an area with many copies of an asset in one call: a large floor, a forest, a field of rocks. pattern "grid" lays them every spacing metres and covers the size; pattern "random" places count of them, at least spacing apart, with the same result for the same seed. A single undoable step. Use this for open spaces rather than listing objects one by one.

scripts_reference¶

Read this before writing a script: how game scripts work, with every function they can call and an example. Whatever rules the user's game has are written as scripts: how characters behave, pickups, doors, score, HUD, and an ending if it has one.

scripts_set¶

Create or replace a game script, as one undoable step. It runs when the game runs, and is refused if it does not compile, with the line of the error. Keep related logic in one script.

screens_set¶

Create or replace an interface screen of the game, as one undoable step: a score, an ammo bar, a help panel, a workshop menu. The user sees it and changes it with the mouse in the editor (Game tab, Interface screens): prefer it to game.hud_* calls in a script for an interface that does not change shape. The engine places it like the HUD, and makes it live without code: bound values, buttons that send their event, screens shown or hidden by an event or a control. To rename it, give its current name in name and the new one in screen.name. screen = {name, visible (shown from the start, default true), show_on: [events], hide_on: [events], toggle: a control name that opens and closes it, cursor (shows the mouse cursor while shown, for buttons), pause (pauses the world while shown), elements: [...]}. element = {name (unique in the screen, no /), kind: text|button|bar|image|panel|input, parent: a panel of the screen (it then places the element; anchor only aligns it left, center or right), anchor: top_left|top|top_right|left|center|right|bottom_left|bottom|bottom_right (the point of the screen holding it, and of the element: it stays in that corner on every screen shape), offset: [x, y] from that point in fractions of the screen (x of the width, y of the height; [-0.02, 0.03] from top_right), w, h (fractions of the width and height), auto_w, auto_h (fit the content; a button or field in a panel takes the panel's width), text ([b]bold[/b], [color=#rrggbb]...[/color]), size (text height, fraction of the screen height; left out: the Interface theme), color, text_color (#rrggbb; left out: the theme), opacity, image (a project image file), placeholder, max_length, value (bar, 0 to 1), layout: column|row|grid, columns, gap, padding, scroll, event (button: the event sent on click, with {cible = "screen/element", ecran, element}; the Trigger reacts to it with quand = evenement), then: nothing|close|open|replace|toggle and then_screen (button: what it does to its screen or another), binding}. UI pack images (assets_search kind image gives each image's size in pixels; never guess it): background (button, panel, bar: an image drawn instead of the color; button: its normal state), background_hover, background_pressed, background_disabled (button states; left out: the normal image), disabled (button: greyed out, does not click; scripts change it with game.hud_set(key, {disabled=})), fill_image (bar: the filled part, cut by the value without stretching), fill: left_to_right|right_to_left|bottom_to_top|top_to_bottom, uv: [u0, v0, u1, v1] (0 to 1: the part of the file shown by an image, or by a button's icon image; an icon in a sprite sheet of 4 x 4 cells: [col/4, row/4, (col+1)/4, (row+1)/4]), slice: [left, top, right, bottom] (a stretchable 9-slice frame for the background, an image and the bar fill: margins in pixels of the image, the corners keep their size, the edges and middle stretch), slice_edges: stretch|repeat, slice_scale (corner size: 1 is one image pixel per screen pixel at 1080 pixels high). binding = {source: event|value|system, name (the event, such as sante.change; the value a script sets with game.set_value; the system), field (the field read: vie), target (event: joueur, an object's name, or empty for anyone; system: the object carrying it, joueur by default), max_field (the field giving the maximum: max) or max (a number), format (text: "Vie : {valeur} / {max}"), decimals}. Scripts reach a screen with game.screen_show, game.screen_hide, game.set_value and game.hud_set("screen/element", {text=...}).

screens_get¶

Read the interface screens of the game. Without a name, lists them; with a name, returns the whole screen in the format of screens_set.

screens_delete¶

Delete an interface screen, as one undoable step.

scripts_get¶

Read the game scripts. Without a name, lists them; with a name, returns its code.

modules_list¶

List the tested game modules shipped with the editor, such as health or inventory: what each does, its settings, the events it sends and listens to, and whether this game uses it. Prefer adding a module to rewriting what it does. Add one only when the user asked for what it does, or agreed to it.

recipes_get¶

Tested Luau recipes for common behaviors: game phases, waves, door and key, timer, dialogue, trigger zones. Without id: the list, with when to use each. With id: its code and notes. Read the list before writing such a behavior yourself, then adapt the recipe to the user's game: its names, tags and values.

modules_info¶

Read how to use a module: its notes for you, and the fields of the events it sends and listens to.

modules_add¶

Add a module to this game, with the modules it needs, as one undoable step. Its scripts become ordinary scripts of the game, which you and the user may change. settings: only those to change from their defaults.

modules_remove¶

Remove a module and its scripts from this game, as one undoable step, even if its scripts were changed. Refused while another added module needs it.

systems_attach¶

Place an activated module on objects or groups, with their values: each object or group has its own (an early skeleton and a boss do not have the same health). Placed on a group, it applies to all its children; a child can change a value for itself with systems_set. Modules it needs on the same object are placed too. values: only those to change from the defaults, among the module's settings with scope "object". One undoable step.

systems_set¶

Change the values of a module on one object or group. A value set to null is no longer changed here: it comes back from the group, or the default. Setting a value on a child of a group that carries the module makes this child differ from the others. One undoable step.

systems_detach¶

Remove a module from one object or group, with its values. Its children no longer carry it, unless placed on them. One undoable step.

systems_inherit¶

Cut or restore, on one folder or object, the inheritance of a module from the folders above it. Cut: neither it nor what it contains receives the module or its values from above; it can then carry its own, starting from the defaults (systems_attach). Example: Health on "Plants", cut on its subfolder "Bushes", then Health with less health placed on "Bushes". One undoable step.

systems_get¶

Read the modules that apply to an object, placed on it or on one of its groups, with its final values and where each comes from: this object, a group, or the default.

modules_set¶

Change the game-wide settings of a module added to this game (scope "game"). Values per object or group go through systems_set. Only the given settings change, as one undoable step.

scripts_delete¶

Delete a game script, as one undoable step.

entities_update¶

Change objects: asset, position, rotation, scale, name, color, collider, tags, visible. Only the given fields change. A single undoable step. Either list updates by id, or change every object matching where with the same set of values: use this to change a whole floor at once.

prefab_create¶

Make a reusable object from an object and everything it contains: build one house, then place as many copies as you like with entities_create or entities_scatter and the asset "prefab:Name". Nothing moves. Correcting one copy and calling prefab_apply corrects them all.

prefab_list¶

List the reusable objects of this scene: their pieces, their copies, and which copies were changed without being applied.

prefab_apply¶

Make this copy the new definition: every other copy takes the same pieces, each keeping its own place. Give the id of the copy, or of a piece in it.

prefab_revert¶

Give this copy back the shape of its definition, losing its changes. Its place, name and tags stay.

prefab_detach¶

Make this copy ordinary objects, which no longer follow the definition.

prefab_delete¶

Delete the definition of a reusable object. Its copies stay in the scene, as ordinary objects.

entities_group¶

Put objects in a new folder object, as a single undoable step: a house made of walls and a roof becomes one thing to move, turn, duplicate or ground. Give ids, or a where filter. The objects do not move.

entities_ungroup¶

Take the objects out of a folder object, and delete the folder. The objects do not move.

entities_delete¶

Delete objects, by ids or by a where filter, as a single undoable step. What they contain is deleted with them. The player cannot be deleted.

entities_ground¶

Rest objects on the surface below them, by ids or by a where filter, lowest first, so stacks settle correctly. A folder goes down as one block, keeping its shape.

animation_files_search¶

Search the animation clip files in the library. Give character_asset to learn, for each file found, whether it was made for that character's skeleton (skeleton_fit): a file with the same bone names but other bone lengths is adapted to the character (adapted_to_character: its rotations only, the hips scaled), and fits; a file made for a skeleton whose bones have other names (Mixamo, Unreal, Blender, Unity...) is borrowed through a bone map found from the names and the shape of both skeletons (borrowed_from_other_skeleton), and fits too: check it with animation_clips. With borrowAnimations off (player_set), only files with the same bone names fit.

animation_clips¶

List the clips in an animation file, with their durations for a character's skeleton, and whether the file was made for that skeleton (skeleton_fit). Use a file only if it fits. One made for other proportions of the same skeleton is adapted to the character (adapted_to_character): it fits, played with the character's proportions. One made for a skeleton whose bones have other names is borrowed (borrowed_from_other_skeleton): bone_map then says which bone of the file each body bone of the character follows, found by name or by shape; fix a bone marked check, or a wrong one, with player_set boneMap {character bone: file bone, or "" for none}.

player_set¶

Choose the controlled character and tune it. Every field is optional and merged with the current values, as one undoable step: if any value is refused, nothing changes. animation is the state graph, and from may be "*". The first valid transition wins. Condition parameters: speed, speedFraction, verticalSpeed, grounded, airTime, jump, moveInput, run, stateTime, stateProgress, forwardSpeed and sideSpeed (m/s seen from the character: negative backwards, positive to its right), strafing (1 while it faces the camera). A state may have back, left and right clips, and the diagonals forwardLeft, forwardRight, backLeft, backRight (8 directions when the file has them), blended by direction while the player faces the camera (faceCamera, or faceCameraAction held): walking sideways and backwards. placeFeet sets the feet on slopes and steps. The default graph has the states idle, walk, run, jump_start, air, land, using clip names that only suit some models (Idle_A, Walking_A, Running_A, Jump_Start, Jump_Idle, Jump_Land): with any other model, read its clips with animation_clips and give your own graph.

world_set¶

Change the game's window, lighting, simulation, camera planes and character walking (navigation). Only the given fields change, as one undoable step.

translations_get¶

Read the game's translations: its original language, the languages it offers, and every text the player sees (found in the systems' settings, the title, the controls' names and game.t("...") in scripts), each with where it appears and its translation in each offered language, or null when missing. The systems' own texts (the Menu's "Jouer", the Map's "Carte"...) are listed too, in the original language, with "builtin": what the system already says in other languages (French, English), shown to the player while the table has no translation for that language: they are not missing there, but translate them for every other offered language, and you may replace a built-in one. Call it before translations_set.

translations_set¶

Write translations into the table of one offered language: the text exactly as written in the game (from translations_get), and its translation. An empty translation removes it. Keep the [b]...[/b] and [color=...] tags and the {1}, {2} or {outil} marks of the original. The table is a file of the project: this is not undone by history_undo.

controls_list¶

List the game's controls: every action the scripts read with game.action, game.pressed or game.released, its key, its gamepad button, the name the player sees, and where it comes from: the game, a module that declares it (combat.basique: block), or the engine (moving, running, jumping, pause on Escape).

controls_set¶

Add a control to the game, or change one: one per key the game uses, never a key read directly. name is what scripts read (game.pressed("open_inventory")); key is a key name from controls_list (e, i, tab, f1, space, lshift, mouse_left, mouse_right, wheel_up...); pad a gamepad button (pad_a, pad_y, pad_lb, pad_up...); label the name the player sees in a key menu, in the user's language ("Open the inventory"). Changing a control a module declares, or a movement, keeps its name and sets the game's own key.

controls_remove¶

Remove a control the game added. A control declared by a module, or a movement, cannot be removed: change its key with controls_set instead, or remove the module.

mixer_set¶

Change the game's sound mixer (game settings, Sound mixer section; scene_get shows it in world.mixer). Every sound belongs to a group: music, effects, ambience, voice, ui are always there, and the user can add more (a radio, a boss's voice). groups: each item changes the given fields of the group with that id or name, or adds a group with a new id: volume 0..1 (the game's balance; the player's options menu multiplies it), muted, muffle 0..1 (always muffled, like a radio behind a wall: 0 clear, 1 under water), label (the name the user sees). remove: ids of added groups to delete (the five default groups stay). ducking replaces the automatic lowering rules: while a sound of when plays, lower goes down to level of its volume in attack seconds, and comes back in release seconds (default: voice lowers music to 0.4). In scripts, a sound picks its group with game.sound(file, {group = "ambience"}); game.mute and game.muffle change a group while playing (a cave, under water), and a trigger rule can too. unfocused: what the game's sound does when its window is minimized or the player switches to another window: mute (the default), lower (to unfocused_level 0..1 of its volume) or keep.

terrain_generate¶

Make the scene's terrain (a map with relief and biomes), or give the existing one a new relief. Only when the user asked for a world, a map or a new relief: replacing a terrain loses the user's sculpting and painting, so it needs replace true. Objects resting on the ground follow the new relief; the vegetation of biomes that remain is kept. shape: land (hills to the edges), continent (one land surrounded by sea), continents (several), archipelago (islands). without_biomes: biome ids the world must not have (snow, desert...).

terrain_brush¶

Change part of the terrain, like the user's brushes: raise (a hill), lower (a hollow, a valley), flatten (a building site, a square), smooth, ramp (a slope between two points, like a road up a hill), paint (give a biome to the ground: a sand path, a field). points are world [x, z] centres: several points make a stroke along them, in one undoable step (space them about a radius apart; raise and lower add up where circles overlap). Objects in the area do not move: ground them afterwards with entities_ground (the result lists them).

water_add¶

Fill the hollow under a world point [x, z] with a lake, up to where it would overflow: dig a hollow first with terrain_brush lower if there is none. The lake is an object inside the terrain object.

water_set¶

Change a water object of the terrain (the sea or a lake): its surface height (higher covers more land), its rendering (realistic, or stylized for a low poly game), its look (a ready-made style first, then any setting), its swell, colours, clarity, foam and wakes. The waves you set are the ones the game's floating objects, swimmers and boats follow, in both renderings.

water_remove¶

Remove a water object of the terrain (a lake, or the sea): its area becomes dry land.

vegetation_add¶

Sow a model over a biome, like the user dragging it onto the biome's Vegetation: thousands of plants (trees, bushes, rocks, grass), placed by themselves, drawn in one go, editable by the user plant by plant. Use this for forests and any repeated nature on a terrain, never entities_scatter. It makes a plant kind object inside the biome: attach systems to it to give them to all its plants (collecte for trees to chop). Returns the plant kind's id and how many plants it sowed.

vegetation_set¶

Change a plant kind (density, sizes, slope, sinking, trunk, draw distance), as one undoable step. Changing the density resows it: plants the user edited by hand may move.

vegetation_remove¶

Stop sowing a plant kind: its plants and its object go away, with the systems attached to it.

scene_validate¶

Check the scene without changing it: player, colliders, ground under the player, animation clips, whether every object is connected to the ground, and whether characters that walk (game.walk_to) stand on walkable ground the player can reach. Fix every error before game_run.

timeline_set¶

Create or replace an animation made by hand, or a cutscene, as one undoable step. The engine plays it; the user sees it on the timeline at the bottom of the editor and edits it with the mouse. kind animation: object tracks only (and events): a door that opens, a platform that rises or comes and goes, a drawbridge, a blinking object. kind cutscene: also cameras, characters, sounds, subtitles and events; while it plays the player has no control, and gets it back at the end. Each object track has keyframes per channel: position, rotation (degrees, as rotation_degrees), scale, visible (always step), color ([r, g, b] 0 to 1). Give them in the WORLD, as entities_update would: they are stored relative to the object's parent, so moving the parent later keeps the animation. A channel without keys does not change the object. Its children follow it. Rotation from 0 to 360 is a full turn. Play it from the Trigger (actions animation / cinematique, with an event at the end), from a script (game.play_timeline), or from the start with autoplay. Check it with view_capture (timeline, time) and in game with game_run (play_timeline on a segment, capture_steps).

timelines_list¶

List the animations made by hand and the cutscenes of the open scene: id, name, kind, length, how it plays, its objects and cues, and what it names that no longer exists.

timeline_get¶

Read one animation or cutscene in full, in the format of timeline_set, with values in the world: to change it, edit this and give it back.

timeline_delete¶

Delete an animation or a cutscene, only when the user asks. Trigger rules and scripts that play it then fail: fix them.

scene_save¶

Save the scene file. The user's scene is otherwise only changed in memory.

history_undo¶

Undo the last change, whether made by you or by the user.

history_redo¶

Redo the last undone change.

material_list¶

List the materials: those of the project (files materials/*.wmmat, with how many objects use each) and the starter library (stone, wood, metal, grass, sand, snow, dirt, rock... real PBR textures, CC0). A starter material is copied into the project the first time you use it, by its path, in material_apply, material_set (from) or terrain_materials.

material_set¶

Create a project material, or change one: every object and terrain layer using it changes with it (a shared material). Give path to change an existing one; otherwise name makes a new file. from copies a starter material (or another one) as the starting point, with its textures. placement world lays the textures by the world on the three axes, without stretching on scaled objects (best for walls, floors, rocks); model follows the model's UVs.

material_apply¶

Put a material on objects (base shapes or models): it replaces the model's own materials, on all its parts. material is a project path or a starter library path (copied into the project); an empty string gives the objects back their model's materials.

terrain_materials¶

Cover the terrain with real materials instead of the flat colors of its biomes, and set them up. cover gives each biome a starter material (grass, rock, snow, sand, mud) and three automatic rules (rock on slopes, snow on peaks, sand by the water). Then: add materials as layers (16 at most), set the material of a biome, replace the automatic rules, or turn it all off. Rules apply in order, the last one wins; hand painting (terrain_paint_material) wins over all of them.

terrain_paint_material¶

Paint a material on the ground, over the biomes and the automatic rules, like the user's Materials brush: area fills a polygon (a field, a square, a beach), path follows a line (a road, a river bank: points are its bends, radius half its width), dabs paints a circle at each point. erase gives the ground back to the biomes and rules. One undoable step.

terrain_material_at¶

Read what covers the ground at world points [x, z]: the dominant material, the share of each layer (biome, automatic rules and painting together), and how much of it is painted by hand.

world_map¶

Read a summary of the whole map, made for large worlds that are too big to read object by object: its size, a text map of the ground (one letter per region, ~ for water), where the objects are (one character per 256 m tile), the sectors with their objects, and the large-world settings. Call this first on a large map, then read one part at a time with area_get. For an image of the whole map or of a sector, use view_capture with view top and area.

area_get¶

Read one part of the map instead of the whole scene: a sector, a 256 m tile, a rectangle or a circle's square. Returns how many objects stand there, grouped by name, what the ground is like (heights, regions, water, steep share), the sectors it touches, and one page of objects (placed objects: a building counts once, with its parts counted). Use name_contains, tag, limit and offset for the next pages; summary_only to skip the list. Without area, the sector you focus on.

sectors_list¶

List the sectors of the map: named rectangles the user and you use to find your way, to work on one part at a time, and to lock what must not change. For each: its limits, how many objects stand in it, and whether it is locked. Says which sector you focus on.

sector_create¶

Create a sector: a named rectangle of the map, in the user's language (Harbour, Old town, North forest). Give its limits as min and max [x, z], as a tile "x_z", or as center and radius. focus: true works on it at once (sector_focus). A single undoable step.

sector_set¶

Change a sector: rename it, move its limits (min and max, or tile), or lock and unlock it. A locked sector refuses every change in it, to the user and to you, until it is unlocked: lock or unlock only when the user asks. A single undoable step.

sector_delete¶

Remove a sector, only when the user asks: its objects stay where they are. Refused for a locked sector. A single undoable step.

sector_focus¶

Work on one sector: scene_get then lists only its objects (and counts the rest), area_get reads it by default, and creating objects outside it is refused unless you give outside_focus. The user sees it in the editor, where the other sectors are hidden. An empty sector works on the whole map again. Not an edit: nothing to undo.

entities_fill¶

Fill a part of a large map with copies of an asset or a reusable object (prefab:Name), by rules instead of by hand: a forest on the hills, rocks in the mountains, houses on flat dry land. Copies stand on the ground, at least spacing apart, and only where every rule holds: regions (biomes), slope, height, away from water, away from what is already there (clearance). count or density_per_hectare says how many. The answer counts what each rule turned down, to adjust. A single undoable step, in one folder.

entities_place_along¶

Place copies of an asset or a reusable object (prefab:Name) along a path on the ground: lamp posts along a road, a fence, a row of trees, houses facing a street. points is the path [[x, z], ...]; a copy every spacing metres, at each sideways offset (left is negative, right positive: [-7, 7] for both sides of a road). facing turns the model's forward axis (+z): along the path, toward it, away from it, or random; add yaw_offset_degrees if the model faces another way, and check with view_capture. Spots under water are skipped. A single undoable step, in one folder.

large_world_set¶

The settings of a large world in one place. large_world saves the scene in 256 m pieces and lets far objects sleep in the game. activity_radius_m: how far around the player things stay awake (300 m by default, the same on every computer). always_active_systems: systems whose objects never sleep. always_active turns objects on or off as always active (a messenger crossing the map, a patrolling boss): keep them few, they cost every step. always_active_budget: how many may stay awake before scene_validate and the editor warn (100 by default; advice, not a limit). Only the given fields change, as one undoable step. The answer says how many objects are always active, counted as the game does (the tag, or a system of always_active_systems).

shader_list¶

List the creator shaders: those of the project (files shaders/*.wmshader in code, shaders/*.wmgraph in connected blocks: whether each passed the three checks, its problems by line (and block), its params, how many materials use it) and the ready-made recipes shipped with the editor (hologram, dissolve, wind in foliage, glowing rim, stylized water, lava, blinking), each in code and in blocks. A recipe is copied into the project by shader_set (from). Prefer a recipe and its params to writing a shader; when the creator works with blocks, take the .wmgraph one.

shader_get¶

Read a creator shader: its code, its params, and whether it passed the three checks (with the problems, by line). path is a project shader or a recipe path from shader_list. For a .wmgraph: graph (the blocks, as JSON) and code (what the blocks become, read-only); a problem names its block.

shader_set¶

Create or change a creator shader of the project: shaders/<name>.wmshader with code (the whole text), or shaders/<name>.wmgraph with graph (the whole block graph, as JSON: see shader_blocks), or from (a recipe path or another project shader) to start from it. The answer is the result of the three checks (text, sandbox, the engine's real shader) with messages by line: when refused, the file is still saved but objects keep the last valid version (or their base material); fix the lines and call it again before saying it works. Never change a shader from a pack: copy it with from. Then put it on a material with material_set (shader, shader_params) and look at it with view_capture (two moments for a moving shader).

shader_blocks¶

The blocks of a .wmgraph shader (the connected blocks the creator sees in the Blocks window): each type, its name and tooltip as shown to the creator, its inputs (with the value a free input takes), its fields, its output size, and where it works (surface, vertices). Read it before writing or changing a graph.

library_search¶

Search the online asset library for free 3D models (CC0 or CC BY), in the sources the user enabled (the Online folder of the Assets panel). The search runs on this computer: every word must match the name, author, category or tags. Returns ids for library_add, with each model's author, licence, source and download size. If no source is enabled, tell the user they can enable one in Assets > Online > Sources; never ask for an address yourself. Prefer the user's own library (assets_search) when it has what is needed.

library_add¶

Download one model of the online library into the project, with its licence: the files are checked (size, fingerprint, format), read by the engine, and copied into assets/ with a LICENCE.txt next to them. Returns the asset path to use with entities_create, and its author and licence. A model already in the project is not downloaded again. Tell the user what you added, by whom, and under which licence: a CC BY model must be credited, and the game export lists the credits for them.

pose_layers_get¶

Read a skinned model's skeleton and its pose layers. A pose layer is a hand correction added on top of the model's animations: a few bones turned by an angle (degrees around the character's own axes at rest, facing +Z: x points to its left, y up, z forward; +x leans an upward bone such as the back or neck forward, and swings a hanging arm backward: -x brings a hanging arm or leg forward). It applies to one clip (clip), to every clip (no clip) or to the seated pose the game builds on a vehicle (clip "@conduite"), with a weight from 0 to 1, for every character using this model (player, characters, other players). Returns each bone with its role (hips, spine, left_hand...), side and parent, and the layers.

pose_layers_set¶

Replace all the pose layers of a skinned model, as one undoable step (read them first with pose_layers_get, change what is needed, send the whole list). Each layer: name, clip (a clip name, none for every clip, "@conduite" for the seated vehicle pose), weight 0..1, enabled, bones {bone name: [x, y, z] degrees}, positions {bone name: [x, y, z]} to move the hips (or a root) in model units, around the character's axes (e.g. [0, -0.1, 0] crouches by 10 cm on a model in metres), and optionally mirror "left_to_right" or "right_to_left" to copy one side onto the other. Small angles (5 to 30 degrees) are usually enough. Game scripts can switch a layer per character with game.pose_layer(id, name, weight). An empty list removes them all.

skeleton_animation_get¶

Read the moves (skeleton animations) made in the tool for a skinned model: files animations/*.wmanim of the project, played like any clip of the model (player animation graph, systems' animation settings, timelines, game.play). Without name: the list of the model's moves, and all its clip names. With name: that move's keyframes, per bone: rotation keys in degrees around the character's own axes at rest (x to its left, y up, z forward; the same angles as pose layers, relative to the rest pose), position keys (hips) in model units relative to rest, ease linear/smooth/step. A clip of the model's files can be read as keyframes too (sampled 10 times per second), to correct it. Read the bones with pose_layers_get.

skeleton_animation_set¶

Create, replace or remove a move (skeleton animation) of a skinned model, as one undoable step. It is saved as animations/<name>.wmanim and plays like any clip of the model, under its name: in the player animation graph, the systems' animation settings (gathering, combat, enemies, dialogue...), timelines, game.play. bones: {bone name: {rotation: [{t: seconds, v: [x, y, z] degrees, ease: linear|smooth|step}], position: [{t, v: [x, y, z]}]}}: rotations around the character's own axes at rest, relative to the rest pose (like pose layers; small angles, 5 to 40 degrees); position for the hips only, in model units. Given bones replace the move's bones (merge: true keeps the other bones). from_clip starts from an existing clip of the model (sampled 10 times per second). A looping move whose channel starts at t=0 goes back to its first key at the end: a walk cycle needs keys for contact, passing, opposite contact, passing. mirror left_to_right copies the left side's rotation keys onto the right side, seen in a mirror (for a walk, give the other side opposite phases by hand instead). remove: true deletes the move. To put a point somewhere rather than compute angles, use move (any bone: the hips move, a hand or a foot bends the two bones above it, a middle bone turns the bones carrying it) or reach. Check the result with view_capture or game_run captures.

skeleton_fix_get¶

Read a skinned model's skeleton at rest and its corrections. Many models (above all auto-rigged ones: Meshy, Mixamo auto-rig) have joints placed beside where the limb should bend: a knee behind the leg, an elbow inside the arm. A correction moves or turns a joint inside the model at rest without moving the model (the skin stays where it is), removes a joint (its skin goes to its parent) or adds one (an attach point for a weapon, or a bone that takes the skin around it). Every animation then bends around the corrected joints. Returns each bone (name, parent, role, rest position in model units, the same units as move and position), the skeleton size, and the current correction.

skeleton_fix_set¶

Correct a skinned model's skeleton, as one undoable step; the model file is never changed (the correction is stored in the project, per model, and follows the model when it is renamed). Read the bones first with skeleton_fix_get. Operations, all optional, applied in this order: reset (true: back to the original skeleton, before the others); restore (bone names: their correction and removal are undone); place ({bone: [x, y, z]}: put the joint at this rest position, in model space and model units; its children follow unless alone); bones ({bone: {move: [x, y, z] model units, turn: [x, y, z] degrees around the character's axes, alone: true to leave its children where they were}}: replaces that bone's correction); remove (bone names: the joint disappears, its skin goes to its parent, its children are attached to the parent at the same place; the root cannot be removed); add ([{name, parent, position: [x, y, z] rest position in model units, skin: true to take the parent's skin beyond it, so it bends that part like a tail tip; without skin it is an attach point for game.attach / hand_bone}]). Animations of the file, borrowed animations, .wmanim motions and pose layers then bend around the corrected joints.

game_run¶

Play the game without a window, with scripted inputs, and report what happened: position, jumps, animation states, and what the scripts did: errors, game.log lines, HUD contents, objects left per tag, events sent (counted by name, and per target for events with a cible field, with the first and last step: hits taken before falling), what the characters driven by scripts did (metres walked, still present or not, the step they were removed), the videos that played (file, full screen or in the HUD, seconds watched, and whether they finished, were skipped or stopped), and the outcome (won or lost, at which step). The same inputs always give the same result. A segment with fight plays like a simple player: it walks to the nearest object carrying fight.tag (a system counts: @ennemis) that is still there and has not received sante.mort, and presses the attack when in reach. The report's fight part lists each target it struck: its first press, how many presses, and the step it fell (sante.mort, or removed), so the time an enemy takes to fall does not depend on the game's events. Use it to measure a fight: how long an enemy takes to fall, how long the player survives. A segment with no move and no action measures what happens when the player does nothing. Each input segment holds for a number of simulation steps (60 per second by default). move is [right, forward], relative to the camera, which starts behind the character. capture_steps returns an image of the game at those steps (4 at most); while the game shows the cursor, the image draws it where the segment put it. To test an interface, show the cursor from the game, then move it with mouse and click with buttons: drag and drop is a press, segments that move the mouse with the button held, then a release. The scripts part has a profile: each script (systems included) with its cost per step in milliseconds (average_ms, worst_ms, percent_of_step), the worst share of its time budget it used (time_budget_used_worst, 1 means stopped as an endless loop), its memory, and near_limit when it gets close to a limit; the heaviest comes first. Times are measured on this machine and vary a little between runs: compare scripts with each other, and optimise the ones at the top. To understand a bug without adding game.log lines, use inspect: at each point (script, line, from step), the game notes the script's variables just before that line runs (locals of the function and of its callers, the script's globals, shared) and goes on; scripts.inspections returns them, or reached: false if the line never ran. Several players (a game with the Multiplayer setting): players adds simulated players to the same game, without a network, as guests of the host: each one joins at join_step, plays its own inputs (the same segments) and leaves at leave_step. The report's scripts.players.guests lists each one: where they are, how far they walked, what they drive, whether they swim, have a menu open, and their own HUD (hud: key -> text). The same inputs give the same game.

scenes_list¶

List the scenes of this game: one per place (a village, a house inside, a cave, a level). For each: whether it is open, whether the game starts there, its arrival points, and its passages (where each leads). Every other tool works on the open scene.

scene_open¶

Open another scene of this game to work on it. Refused while the open scene has unsaved changes: call scene_save first. The player, systems, scripts and game settings stay the same: they belong to the whole game.

scene_create¶

Create a new, empty scene in this game: another place, such as the inside of a house, a cave or a next level. Its name is a file name (no / \ : * ? " < > |). It opens unless open is false. Delete a scene of this game, only when the user asks. It is set aside in the project's work folder, not erased. Refused for the start scene, the last scene, and the scene that holds the player's character. The answer lists the passages and scripts that still lead to it: fix them.

game_export¶

Build a standalone Windows copy of the game, which runs without the editor, in the export folder beside the scene, and check that it starts. view_capture¶

Look at the scene as it is in the editor, and get an image back. view: perspective, top, bottom, front, back, left, right. mode: normal, polygons, wireframe. Frames the given objects, or the whole scene. For perspective, yaw_degrees turns around the scene, and pitch_degrees is the height of the camera above the horizon: positive looks down from above (30 by default), negative looks up from under the ground. If an image looks dark, check the camera before changing the lighting. camera_id looks through a placed camera, as the game will: view, focus_ids, yaw and pitch are then ignored. timeline and time show an animation or cutscene (timeline_set) at that second: its objects posed as the game will pose them, and a camera it moves where it is then. area frames one part of a large map instead of objects: a sector, a 256 m tile or a rectangle; view top gives the map seen from the sky, perspective with a low pitch_degrees (5 to 10) a view across it close to eye level.
